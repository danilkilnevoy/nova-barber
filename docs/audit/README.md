## 3. Core Web Vitals

Замер выполнялся на главной странице в чистом профиле браузера: запись сессии ~10 секунд, во время которой выполнялись реальные взаимодействия — клики по заголовку и карточке, наведение на CTA, 4 нажатия `Tab`, 3 нажатия `ArrowDown`, прокрутка и повторный клик. Значения сняты через **Event Timing API** (`PerformanceObserver`, тип `event`) и **Layout Instability API** (`layout-shift`) — это те же источники данных, которые использует панель Performance в DevTools.

**Таблица 3 — Core Web Vitals (главная страница, реальные взаимодействия)**

| Метрика                             | Значение            | Порог «хорошо» | Статус  |
| ----------------------------------- | ------------------- | -------------: | ------- |
| **LCP** (Largest Contentful Paint)  | **0.58 с** (576 мс) |        ≤ 2.5 с | в норме |
| **INP** (Interaction to Next Paint) | **184 мс**          |       ≤ 200 мс | в норме |
| **CLS** (Cumulative Layout Shift)   | **0.065**           |          ≤ 0.1 | в норме |
| FCP (для контекста)                 | 544 мс              |        ≤ 1.8 с | в норме |
| TTFB (для контекста)                | 29 мс               |        ≤ 0.8 с | в норме |

**Детализация:**

- **LCP-элемент** — `<img>` с фоновым изображением hero-блока (Supabase Storage).
- **INP** — худшее взаимодействие 184 мс; остальные пять взаимодействий уложились в 16 мс. Длинных задач (`longtask`) за сессию — **0**.
- **CLS** — 3 сдвига, из них основной 0.0639 в момент 534 мс (подстановка изображения/шрифта), остальные два — 0.0008 и 0.0002, то есть визуально незаметны.

**Разница с Lighthouse:** в Lighthouse LCP главной = 0.77 с (медиана), здесь — 0.58 с. Причина в том, что Lighthouse применяет **симулированное троттлинг-ограничение** сети и CPU, а замер через PerformanceObserver шёл на локальном контуре без замедления. Оба значения далеки от порога 2.5 с, поэтому вывод не меняется: **все три метрики в «зелёной» зоне**.

После исправлений (раздел 7) метрики перезамерены: LCP 0.58 с, INP 184 мс, CLS 0.065 — изменения в пределах погрешности, что ожидаемо: правки касались цвета текста и уровней заголовков.

Закрыты служебные страницы и API, директива `Sitemap:` указывает на корректный адрес. **До исправления** здесь стоял `https://example.com/sitemap.xml` (см. раздел 7, проблема № 4).

`/account.html` и `/login.html` содержат `<meta name="robots" content="noindex">` — подтверждено в отдаваемом HTML. Дополнительно обе страницы закрыты в `robots.txt`, а `Disallow` и `noindex` вместе дают надёжную защиту от индексации.

### 4.5 X-Robots-Tag для API

Заголовки ответа `/api/health`:

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-Robots-Tag: noindex, nofollow
```

Заголовок выставляется nginx (`add_header ... always`) для всей зоны `/api/` — API не попадёт в индекс даже при прямом обращении.

## 5. Доступность

### 5.1 Навигация с клавиатуры

Проверено последовательным нажатием `Tab` на главной странице. Порядок обхода:

1. Логотип в шапке (ссылка на главную).
2. Пункты меню: Главная, Услуги, Барберы, Онлайн-запись, Контакты — 5 элементов подряд.
3. «Личный кабинет».
4. CTA «Записаться онлайн».
5. Логотип в подвале.

Все девять элементов получают **видимый фокус**. После последнего элемента фокус уходит на `body` и затем циклически возвращается к шапке — «ловушек фокуса» нет, все элементы достижимы, порядок соответствует визуальному. Индикатор фокуса — стандартный `outline: 1px auto` от браузера, он **не подавлен** стилями (`outline: none` в CSS отсутствует).

Кнопка-бургер мобильного меню скрыта на десктопе, но размечена корректно: `aria-label="Открыть меню"`, `aria-expanded`, `aria-controls="mainNav"`, `type="button"` — при переходе на мобильную вёрстку она доступна и с клавиатуры, и скринридеру.

**Пояснения к таблице 7**

- **№ 1–2 (контраст).** WCAG AA требует 4.5:1 для обычного текста. № 1 — `#786f63` на фоне `#f3eee2` на всех 7 страницах; № 2 — `#c5aa87` на белом (номера шагов 01/02/03 в форме записи).
- **№ 3 (заголовки).** Нарушен порядок: `<h3>` шёл сразу после `<h1>`, минуя `<h2>`. Ломает навигацию по заголовкам в скринридерах.
- **№ 4 (домен).** Карта сайта ссылалась на несуществующий хост `example.com` — поисковик отклонил бы файл целиком, при этом Lighthouse ставил SEO 100.

## 8. Выводы

1. **Проект в хорошем техническом состоянии.** Все четыре категории Lighthouse на публичных страницах — в диапазоне 94–100 (медианы): Performance 94–99, Accessibility 92–95 (после правок — 100), Best Practices 100 на всех страницах, SEO 100 на всех публичных страницах.

2. **Core Web Vitals — все три метрики в «зелёной» зоне:** LCP 0.58 с (порог 2.5 с), INP 184 мс (порог 200 мс), CLS 0.065 (порог 0.1). INP — самая близкая к порогу метрика: запас всего 16 мс, и при утяжелении JS он уйдёт в «жёлтую» зону первым. Длинных задач за сессию не зафиксировано, TBT = 0 мс на всех страницах.

3. **SEO-база закрыта корректно:** уникальные title и description на всех страницах, `lang="ru"`, `charset`, `viewport`, `noindex` на служебных страницах, `X-Robots-Tag` на API, рабочие `robots.txt` и `sitemap.xml`. Категория SEO — стабильно **100**.

4. **Главная проблема была в доступности**, и она исправлена: контраст текста (WCAG AA) и порядок заголовков. Это дало +6…+8 баллов Accessibility при трудоёмкости в несколько строк — самый выгодный тип правок в этом проекте.

5. **Найден и устранён скрытый SEO-дефект, который не видит Lighthouse:** домен-заглушка `example.com` в `robots.txt` и `sitemap.xml`. Категория SEO оставалась 100, потому что Lighthouse проверяет наличие и валидность файлов, но не сверяет домен внутри них с текущим хостом. Это иллюстрация того, почему автоматический аудит нужно дополнять ручной проверкой.

6. **Сравнение с аналогом в пользу проекта:** 98/94/100/100 против 63/97/74/54. Конкурент проигрывает по SEO катастрофически (54 — страница закрыта от индексации и без meta description) и по скорости (LCP 3.22 с против 0.77 с), но слегка выигрывал по доступности — после исправлений преимущество утрачено.

7. **Что делать дальше (P2):** задать `width`/`height` изображениям и убрать `loading="lazy"` с LCP-картинок на `services`/`barbers` — это самый прямой путь к CLS ≈ 0 и LCP < 1 с; затем self-host шрифтов вместо Google Fonts CDN, кэш-заголовки в nginx, `canonical` и Open Graph.
