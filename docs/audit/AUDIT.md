## 3. Core Web Vitals

Замер выполнялся на главной странице в чистом профиле браузера: запись сессии ~10 секунд, во время которой выполнялись реальные взаимодействия — клики по заголовку и карточке, наведение на CTA, 4 нажатия `Tab`, 3 нажатия `ArrowDown`, прокрутка и повторный клик. Значения сняты через **Event Timing API** (`PerformanceObserver`, тип `event`) и **Layout Instability API** (`layout-shift`) — это те же источники данных, которые использует панель Performance в DevTools.

**Таблица 3 — Core Web Vitals (главная страница, реальные взаимодействия)**

| Метрика | Значение | Порог «хорошо» | Статус |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | **0.58 s** (576 ms) | ≤ 2.5 s | соответствует |
| **INP** (Interaction to Next Paint) | **184 ms** | ≤ 200 ms | соответствует |
| **CLS** (Cumulative Layout Shift) | **0.065** | ≤ 0.1 | соответствует |
| FCP (для контекста) | 544 ms | ≤ 1.8 s | соответствует |
| TTFB (для контекста) | 29 ms | ≤ 0.8 s | соответствует |

**Детализация:**

- **LCP-элемент** — `<img>` с фоновым изображением hero-блока (Supabase Storage).
- **INP** — худшее взаимодействие 184 ms; остальные пять взаимодействий уложились в 16 ms. Длинных задач (`longtask`) за сессию — **0**.
- **CLS** — 3 сдвига, из них основной 0.0639 в момент 534 ms (подстановка изображения/шрифта), остальные два — 0.0008 и 0.0002, то есть визуально незаметны.

**Разница с Lighthouse:** в Lighthouse LCP главной = 0.77 s (медиана), здесь — 0.58 s. Причина в том, что Lighthouse применяет **симулированное троттлинг-ограничение** сети и CPU, а замер через PerformanceObserver шёл на локальном контуре без замедления. Оба значения далеки от порога 2.5 s, поэтому вывод не меняется: **все три метрики в «зелёной» зоне**.

После исправлений (раздел 7) метрики перезамерены: LCP 0.58 s, INP 184 ms, CLS 0.065 — изменения в пределах погрешности, что ожидаемо: правки касались цвета текста и уровней заголовков.

- Title короче рекомендованных 50–60 символов на внутренних страницах (18–28 символов) — снижает информативность сниппета, но не является ошибкой.

- **Отсутствуют Open Graph / Twitter Card** теги — ссылки в соцсетях и мессенджерах не формируют превью.

### 4.2 robots.txt

Открывается как **текст** (`Content-Type: text/plain; charset=utf-8`), не как HTML. Содержимое:

```
User-agent: *
Disallow: /account.html
Disallow: /login.html
Disallow: /api/

Sitemap: https://nova-barber.localhost/sitemap.xml
```

Закрыты служебные страницы и API, директива `Sitemap:` указывает на корректный адрес. **До исправления** здесь стоял `https://example.com/sitemap.xml` (см. раздел 7, проблема № 4).

### 4.3 sitemap.xml

Открывается как **XML** (`Content-Type: application/xml`), валидная структура `<urlset>` с пространством имён sitemaps.org. **5 публичных страниц**, `lastmod` = 2026-10-30, приоритеты 1.0 → 0.7:

| URL | priority |
|---|---|
| https://nova-barber.localhost/ | 1.0 |
| https://nova-barber.localhost/services.html | 0.9 |
| https://nova-barber.localhost/barbers.html | 0.9 |
| https://nova-barber.localhost/booking.html | 0.8 |
| https://nova-barber.localhost/contacts.html | 0.7 |

Служебные `account.html` и `login.html` в карту сайта не включены — корректно.

### 4.4 noindex на служебных страницах

`/account.html` и `/login.html` содержат `<meta name="robots" content="noindex">` — подтверждено в отдаваемом HTML. Дополнительно обе страницы закрыты в `robots.txt`, а `Disallow` и `noindex` вместе дают надёжную защиту от индексации.

### 4.5 X-Robots-Tag для API

Заголовки ответа `/api/health`:

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-Robots-Tag: noindex, nofollow
```

Заголовок выставляется nginx (`add_header ... always`) для всей зоны `/api/` — API не попадёт в индекс даже при прямом обращении.

### 5.1 Навигация с клавиатуры

Проверено последовательным нажатием `Tab` на главной странице — обход всех интерактивных элементов:

| 2–6 | Пункты меню: Главная, Услуги, Барберы, Онлайн-запись, Контакты | да |

После последнего элемента фокус уходит на `body` и затем циклически возвращается к шапке — «ловушек фокуса» нет, все элементы достижимы, порядок соответствует визуальному. Индикатор фокуса — стандартный `outline: 1px auto` от браузера, он **не подавлен** стилями (`outline: none` в CSS отсутствует).

Кнопка-бургер мобильного меню скрыта на десктопе, но размечена корректно: `aria-label="Открыть меню"`, `aria-expanded`, `aria-controls="mainNav"`, `type="button"` — при переходе на мобильную вёрстку она доступна и с клавиатуры, и скринридеру.

### Что исправлено

Исправлены **4 проблемы приоритета P1** (№ 1–4). Логика приложения (`server.js`, `Dockerfile`, `nginx.conf`) не менялась — правки затрагивают только оформление и SEO-файлы.

**1. Контраст текста подвала (проблема № 1).** Токен цвета `muted` затемнён: `#786f63` → `#6f6659`. Контраст на фоне `#f3eee2`: **4.27:1 → 4.88:1** (норма 4.5:1), на белом: 4.94:1 → 5.64:1. ## 8. Выводы

1. **Проект в хорошем техническом состоянии.** Все четыре категории Lighthouse на публичных страницах — в диапазоне 94–100 (медианы): Performance 94–99, Accessibility 92–95 (после правок — 100), Best Practices 100 на всех страницах, SEO 100 на всех публичных страницах.

2. **Core Web Vitals — все три метрики в «зелёной» зоне:** LCP 0.58 s (порог 2.5 s), INP 184 ms (порог 200 ms), CLS 0.065 (порог 0.1). INP — самая близкая к порогу метрика: запас всего 16 ms, и при утяжелении JS он уйдёт в «жёлтую» зону первым. Длинных задач за сессию не зафиксировано, TBT = 0 ms на всех страницах.

3. **SEO-база закрыта корректно:** уникальные title и description на всех страницах, `lang="ru"`, `charset`, `viewport`, `noindex` на служебных страницах, `X-Robots-Tag` на API, рабочие `robots.txt` и `sitemap.xml`. Категория SEO — стабильно **100**.

4. **Главная проблема была в доступности**, и она исправлена: контраст текста (WCAG AA) и порядок заголовков. Это дало +6…+8 баллов Accessibility при трудоёмкости в несколько строк — самый выгодный тип правок в этом проекте.

5. **Найден и устранён скрытый SEO-дефект, который не видит Lighthouse:** домен-заглушка `example.com` в `robots.txt` и `sitemap.xml`. Категория SEO оставалась 100, потому что Lighthouse проверяет наличие и валидность файлов, но не сверяет домен внутри них с текущим хостом. Это иллюстрация того, почему автоматический аудит нужно дополнять ручной проверкой.

6. **Сравнение с аналогом в пользу проекта:** 98/94/100/100 против 63/97/74/54. Конкурент проигрывает по SEO катастрофически (54 — страница закрыта от индексации и без meta description) и по скорости (LCP 3.22 s против 0.77 s), но слегка выигрывал по доступности — после исправлений преимущество утрачено.

7. **Что делать дальше (P2):** задать `width`/`height` изображениям и убрать `loading="lazy"` с LCP-картинок на `services`/`barbers` — это самый прямой путь к CLS ≈ 0 и LCP < 1 s; затем self-host шрифтов вместо Google Fonts CDN, кэш-заголовки в nginx, `canonical` и Open Graph. Проблемы P3 (WebP/AVIF, вынос Supabase SDK только на нужные страницы) дадут ещё несколько десятков KiB экономии.

**Ограничения аудита:** замеры выполнены в headless-Chromium на локальном контуре, поэтому абсолютные значения LCP/FCP ниже, чем были бы на реальном хостинге с сетевой задержкой; сравнение страниц между собой и оценка Lighthouse корректны, так как условия для всех страниц и для аналога были одинаковыми.
